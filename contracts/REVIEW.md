# Contract review — 1.1.0 draft

This review covers the files in this repository. The linked Claude artifact and ChatGPT conversation were inaccessible; their contents have not been verified. This revision is a breaking proposal for team review, not a deployed implementation or a safety certification.

## Authority and migration

JSON Schema Draft 2020-12 files define wire shapes. This document defines additional runtime semantics and overrides conflicting legacy examples in `CONTRACTS.md`. Timestamps use UTC `Z`; validators must enable format checking. Embedded schemas and fixtures must match the standalone files. Handwritten TypeScript examples are illustrative until generated types replace them. Consumers must migrate together; reject unsupported protocol versions and do not silently coerce older workflows.

The draft now defines recursive loop bodies, explicit read outputs and decision references, bounded iteration/retries, required pre/postconditions for writes, conditional locator fields, typed defaults, redaction constraints, closed objects, and a remote command envelope. The demo now reads both decision inputs inside each iteration and includes navigation, tag selection, save, summary drafting, and posting.

## Workflow compilation and execution

- Step IDs are unique across the entire plan; parameter names and rule IDs are unique within their collections. Locator references are zero-based indexes into that step's locator list. Unsupported apps, checks, actions and condition implementations fail compilation.
- `source: "user"` parameters are run inputs. `source: "step:<step_id>.output"` binds a parameter to a prior `read_field` of the same name and type; callers cannot override it. The demo derives `account_ids` from the portal. Run creation accepts `{ "workflow_version": 4, "mode": "supervised", "parameters": {} }` and requires an `Idempotency-Key` header. Reusing a key with different content returns `409 CONFLICT`; matching requests return the original run without executing twice.
- Reject missing/unconfirmed parameters and rules at validation. Validate user values against declared types; reject unknown input names. Treat provenance/trust as server-owned, never as permissions granted by client JSON. Any plan edit increments its version and resets validation/trust. Runs pin the reviewed version and a SHA-256 digest of its canonical JSON.
- Steps run in array order. A loop executes its entire `body` for each ordered input item. `source_param` must name a `string[]` available before the loop; `item_name` is scoped to that iteration. Loop read outputs and `decision.<rule_id>` never leak to later iterations or outside the loop. Freeze the list at entry; exceeding the bound aborts before the first iteration, rather than silently truncating. Reject duplicate record IDs for this demo. Empty lists are valid and still produce the run-specific zero-count summary.
- Each `read_field` publishes a value matching `output_type`. A `string[]` read requires an app adapter that extracts record IDs, not an arbitrary split of visible text. Missing or malformed data pauses execution; do not substitute zero, false, or previous-iteration values.
- Decisions select a literal `then` or `else` value and publish `decision.<id>`; they do not jump to steps. The MVP expression grammar is identifiers, string/finite-number/boolean literals, comparisons (`== != < <= > >=`), `and`, `or`, `not`, and parentheses. No calls, attributes, indexing, arithmetic, imports, assignment, or `eval`. Compile a restricted AST, enforce operand types, and reject unavailable names.
- Templates resolve names only, with `decision.<id>` and array `.length` as the only property forms. A template consisting solely of `{{name}}` preserves type; interpolation into other text produces a string. Reject unresolved placeholders. Encode each URL path value and validate the final scheme, host, port and path against the app allowlist. No arbitrary code, shell, SQL, filesystem path, or executable expression interpolation.
- `run_id` is an immutable runtime value. `expected_tags` is a runtime-owned map: freeze the expected decision for each record before saving, retain it in the checkpoint, and compare independent CRM reads against that map in the final outcome check. Never populate expected values by reading back the actual tags. It is available to outcome checks only. The summary count is the successfully completed account count; the demo can use `account_ids.length` because every loop step is required and no skip is allowed.
- Default step timeout is 10,000 ms; explicit `timeout_ms` is bounded by schema. Every step follows precondition, unique target resolution, action, postcondition. Locator alternatives must identify the same intended target; ambiguity pauses. `locator_ref` is evaluated independently using that locator, not interpreted as the fallback winner. Missing features never degrade silently to coordinate clicks.
- `url_matches` compares the exact resolved pathname on the registered app origin, not a regex or substring. `record_id_matches` uses the adapter's stable record identity. `field_equals` compares the normalized displayed value. `network_2xx` requires a fresh response to the action's expected mutation request on the registered app origin/path, captured by a listener installed before the action. A coincidental GET or an unrelated 2xx is insufficient. State checks and independent final reads remain required.
- Effective risk is the maximum of the step declaration, app/action classification and current policy; a loop's R0 label never lowers child risks. R3 is blocked for all modes. R2 always needs approval; R1 needs approval in supervised mode and may run automatically only under server-earned trusted policy. Unvalidated plans never execute. Remote initiation does not raise trust or bypass approvals.
- Never blindly retry a click or external effect. A lost response produces an uncertain outcome: pause and reconcile against an independent read or app idempotency key before retry. A checkpoint includes pinned plan version/hash, frozen items, nested loop cursor, completed step instances, outputs, expected values, and effect receipts. Persist the execution intent before mutation and receipt afterward. Restart must reconcile the crash window between them; a local transaction cannot make an external application exactly-once.
- Serialize desktop execution to one active run per agent. Observation must not learn the agent's own actions. Lock/logout, kill switch, cancellation or revoked permissions stop further input and invalidate pending approvals. Cancellation cannot undo completed effects. Resume rechecks session, policy, target, record and preconditions.

## Approvals and remote commands

`command.schema.json` covers shape only. `command.valid.json` contains a zero placeholder signature and fixed timestamp; it MUST NOT pass a real verifier. `command.invalid.json` is structurally invalid, not a cryptographic replay test.

1. Parse strict JSON with duplicate keys rejected, size/depth limits and finite numbers only. Check protocol version 1 and schema before processing commands. Verify Ed25519 using the active paired sender key over `UTF8("digitalghost.command.v1\n") + RFC8785_JCS(envelope_without_sig)`. Only the top-level `sig` is omitted. Use interoperable canonicalization, not language-default JSON serialization. Sign routing fields and version as well as payload.
2. Require `payload.device_id == from_device`, `to_device == this_agent`, valid destination pairing, and command-specific authorization. Key revocation takes effect before every action. The relay cannot authorize anything merely by routing it.
3. Require UTC `issued_at` within 60 seconds of the verifier clock in either direction. Nonces contain 128 bits of cryptographically random data (32 lowercase hex characters). After signature and authorization checks, atomically consume `(from_device, nonce)` in durable storage before execution. Keep it at least ten minutes, across restarts. Concurrent duplicates execute at most once. Retain command IDs/results for idempotent lookup; replays return `REPLAY_DETECTED`, stale timestamps `COMMAND_EXPIRED`, invalid signatures `SIGNATURE_INVALID`.
4. `approve_step` and `reject_step` require an outstanding, single-use `approval_id`, pinned workflow version, run/step identity and `effect_hash`. These fields bind the approval to a specific loop iteration through the unique approval ID. The server computes `effect_hash = SHA256(JCS(effect_preview))` using a versioned preview object containing `preview_version`, `approval_id`, `run_id`, `workflow_id`, `workflow_version`, `workflow_hash`, `step_id`, `loop_path` (ordered `{step_id,index,item}` entries), registered app origin, stable target identity, normalized mutation arguments, and classified risk. The schema uses hex SHA-256. Display the exact effects locally before consent.
5. Approval expires after 60 seconds and is consumed atomically. Any target, record, payload, plan, policy or precondition change invalidates it (`STALE_APPROVAL`); recompute before the action. Rejecting aborts the run. No broad approval of future loop iterations. Local `POST /runs/{id}/approve` and `/reject` accept the same binding fields (`approval_id`, `workflow_version`, `step_id`, `effect_hash`); path run ID binds the run. State/version conflicts return 409; bad shapes return 422.
6. MVP remote commands carry no field values. `params`, if present, is empty. Remote `run_workflow` is limited to reviewed workflows deriving inputs locally or from confirmed non-sensitive defaults. The agent still validates current policy. Remote previews/status must be minimized; hashes and signatures provide no confidentiality. Sensitive previews require the local dashboard until an authenticated encrypted protocol is implemented. Desktop responses must be signed by the pinned desktop key with a distinct response domain separator and request correlation; an unsigned relay message must never be treated as approval or authoritative status.
7. Pairing requires a high-entropy, one-use, short-lived QR capability, proof of possession of the phone key, a desktop confirmation bound to that key, and public-key fingerprint comparison on both devices. The six-digit code in the legacy example is only a display hint, never a bearer credential or fingerprint. Rate limit claims, expire within five minutes, and pin both peer public keys. Disable remote control on unsupported WebCrypto platforms rather than weakening key protection.

## Local HTTP, streams, privacy and storage

- Serve the dashboard at `http://127.0.0.1:7777`; allow its exact Origin and configured extension ID. `localhost` is optional only if explicitly served/configured. Check Host against the loopback service and defend against DNS rebinding. Require Bearer authentication for every data/control endpoint. Browser requests must have an allowed Origin; native/CLI requests without Origin still require authentication. Reject `Origin: null` and foreign origins. CORS preflight can return only configured origins/methods/headers without data; CORS is not authentication. Never place the long-lived token in a URL or remote PWA.
- Browser WebSocket constructors cannot set Authorization headers. `POST /api/v1/stream/tickets` returns a random one-use ticket and UTC expiry 30 seconds later, with `Cache-Control: no-store`. Bind it to the allowed Origin/principal, consume atomically during upgrade, and exclude it from logs. A remote HTTPS PWA communicates via the relay, not a loopback mixed-content connection.
- Stream envelopes add `event_id` (UUID) and monotonic per-agent `sequence` (integer >= 1), alongside `type`, `ts`, and `data`. Event data is a notification, not the canonical run state. On reconnect/gap, fetch REST snapshots before enabling controls. Approval notifications include approval binding fields and expiry; step notifications include loop path to distinguish iterations.
- Ingest batches contain 1–200 events, at most 1 MiB decoded JSON; validate the whole batch before writing. Deduplicate by event ID: same ID/content is a no-op, conflicting content is 409. Response is `{ingested, duplicates}`. Pause observation on lock, excluded apps and consent withdrawal. Redact before transmission, persistence, audit or LLM calls.
- Schema enforces `redacted => text == null`, `secret_omitted => redacted`, and `shape == none => text == null`. It cannot identify secrets. Collectors must remove secrets from URLs, query parameters, labels, window titles, DOM text, clipboard, screenshots and debug logs as well as input values. Allowlist origins, fields and values; omit clipboard contents by default. Consent for observation does not imply permission to send data to a cloud LLM.
- Outcome checks are registered, read-only adapters with fixed argument contracts. `db_query` names a reviewed check; it never contains arbitrary SQL. LLM suggestions are untrusted drafts and cannot add executable checks or permissions. Source redaction and explicit LLM consent precede OmniRoute calls; disabling it keeps deterministic discovery available.
- Workflow updates use optimistic concurrency (`If-Match` with current version/digest); stale updates return 409. Pending approvals and active runs bind immutable versions. Lists use bounded `limit` (1–200) and an opaque cursor. Errors use `error.schema.json` without secrets in details. Data deletion requires local consent, stops affected work, invalidates approvals, and clearly defines which audit records are retained/minimized. Remote devices cannot invoke deletion.
- A local hash chain detects some modifications; it is not tamper-proof against an attacker able to rewrite the database and its head. Stronger claims need a separately protected signed/anchored head.

## Verification and remaining implementation gates

Run `python -m pip install -r contracts/requirements-dev.txt`, then `python contracts/validate.py`. Checks cover schema validity, fixture acceptance/rejection, embedded JSON synchronization, workflow reference/scope checks, expression restrictions, and targeted regression mutations.

The initial review preceded implementation. M2 now has an execution backend, standalone FastAPI host, remote modules, relay router and focused tests; see [the implementation handoff](../agent/M2_IMPLEMENTATION.md) for the supported subset and actual test evidence. The shared application, generated Pydantic models, learning routes, demo apps and a Tauri notch now exist. Contract-equivalent shared authentication, model constraint parity, reviewed workflow admission, real demo-app integration and the full end-to-end suite remain outstanding. See [the 2026-10-22 verification report](../docs/VALIDATION.md) for reproduced gaps and measured build/test evidence. Before freezing the contracts, reconcile the still illustrative Run, approval, pairing, stream and settings structures with all owners. Owner sign-off is still required.

Required integration gates: canonicalization/Ed25519 vectors shared between Python and WebCrypto; altered sender/destination/version/payload; malformed JSON/duplicate keys; stale/future timestamps; nonce races and process restart; key revocation and pairing hijack; approval expiry/changed effect/wrong iteration; missing consent and redaction in all metadata; foreign/missing origins and stream ticket reuse; R3 disguised as R0; uncertain external writes and checkpoint recovery; loop limits, output typing, expression injection; seeded demo outcome verification. The fixture validator alone does not run these gates. M2 unit-test evidence is documented separately in the implementation handoff; it does not replace real-browser and cross-platform integration gates.
